## المطابقة مع 97 صنفًا قديمًا

تقرير اللقطة العامة `docs/audits/live-menu-matching-2026-11-09.csv`: **59** مرشحًا للمطابقة مع أسعار مختلفة، و**36** صنفًا قديمًا بلا مقابل مؤكد، و**2** بصنف ذي حجم/سعر غير محسوم (المجموع 97).

المعاينة التنفيذية الفعلية — وليست تصنيف الملف اليدوي — على هذه اللقطة:

| قرار المعاينة | العدد |
|---|---:|
| إنشاء منتجات مؤكدة جديدة | 54 |
| تحديث سعر/حجم بعد موافقة صريحة | 50 |
| مراجعة يدوية، بدون كتابة | **26** |
| إنشاء إضافة مستقلة للبيتزا | 1 |

الـ**26 مراجعة** = **5** من الصورة + **9** اختلافات أحجام لمنتجات قديمة معروفة + **12** أسماء محتملة التشابه دون هوية مؤكدة. لذلك **59 مرشحًا للمطابقة لا تعني 59 تعديلًا تلقائيًا**.

بعد التطبيق التجريبي بموافقة صريحة على فروق السعر: **151 منتجًا = 97 قديمًا محفوظًا + 54 جديدًا**، و**13 قسمًا** دون إنشاء قسم مكرر لـ«طواجن/الطواجن». إعادة المعاينة ثم التطبيق لا تنشئ منتجات إضافية. الـ**36** القديمة غير المطابقة تحتفظ بمعرّفاتها وأسمائها وأحجامها وأسعارها؛ لا نحذفها أو نخفيها تلقائيًا.

## ضوابط السلامة الحالية

- تطبيق سطر الأوامر محصور بملف المنيو نفسه وببصمته المعتمدة؛ لا يُقبل ملف بديل لمجرد حمل بصمة معاينة صحيحة.
- الكتابة من سطر الأوامر محصورة بملف SQLite محلي منفصل داخل `database/` أو `storage/` واسمه يحتوي `staging` أو `test`. قواعد MySQL والاتصالات البعيدة وذاكرة SQLite لعملية سطر الأوامر مرفوضة. SQLite في الذاكرة **مسموح فقط لاختبارات الخدمة داخل العملية**.
- بصمة المعاينة تتغير مع المصدر أو خطة تغييرات السعر، ولا يُسمح بتحديث الأسعار دون الخيار الصريح. **الخيار ليس توقيع اعتماد مستقلًا**؛ يبقى تدقيق الفروق البشري مطلوبًا.
- مفاتيح الاستيراد تربط منتجًا واحدًا بمفتاح واحد، مع حظر تضارب مفتاحين لنفس المنتج. تحديث سعر موجود يفحص القيمة القديمة قبل الكتابة لتفادي الكتابة فوق تعديل متزامن.
- ترحيل جداول روابط الاستيراد والإضافات يقبل إعادة التنفيذ، والتراجع عنه يحافظ على بيانات الجداول عمدًا. هذه سياسة **غير قابلة للعكس تلقائيًا**، لا تعني حذف البيانات عند rollback.
- التحقق الجديد يرفض تمثيل السعر بصيغة أسية أو أكثر من خانتين عشريتين أو خارج مدى `DECIMAL(10,2)`، ويرفض جعل السعر المطبوع غير المحسوم «مؤكدًا» دون علامة مراجعة.
- **تدقيق متابعة على الالتزام `2e9a619`:** اختباران أكدا أن إعادة تطبيق منيو بلا تغييرات كانت تعيد كتابة `created_at` و`updated_at` لروابط المنتجات، وتحديث الإضافة كان يعيد كتابة تاريخ إنشائها. أصبح استيراد الربط غير المتغيّر بلا كتابة، وتحديث الروابط/الإضافات يحافظ على `created_at` باستخدام إدراج أو تحديث ذري. اختبارات الزمن فشلت قبل الإصلاح ونجحت بعده.
- **فحص حماية الخدمة مباشرةً:** اختبار مستقل أثبت أن `MenuImporter::apply` كان يقبل إعداد `DATABASE_URL` بديلًا ولو رفضه أمر `menu:apply`، عند وجود اتصال اختبار SQLite مسبق في الذاكرة. أصبحت الخدمة نفسها ترفض `url` و`read` و`write`، وتتحقق من برنامج تشغيل الاتصال الفعلي ومسار ملف SQLite المتصل (أو ذاكرته) قبل أي كتابة؛ لا يتم فتح اتصال خارجي للتحقق.

## ما يمنع النشر تلقائيًا

1. **الكمية صفر تعني غير محددة في الصور، لا إثبات نفاد.** الاستيراد يضع `quantity=0` ولا يملك الحقل الحالي قيمة «غير معروف». أُصلح عرض الإدارة ليصف الصنف المستورد ذي الصفر بأنه «التوفر غير مؤكد»، لكن حالة مخزون مجهولة منفصلة لم تُضف لقاعدة البيانات، ولا يثبت ذلك جاهزية أي مسار بيع قديم؛ راجع الكميات قبل النشر. لا تُملأ الحقول بمخزون تخميني.
2. الـ36 صنفًا القديمة غير المطابقة ما زالت موجودة. يلزم قرار منفصل بالأرشفة/الإخفاء، دون حذف بيانات أو روابط طلبات.
3. الـ26 حالة المراجعة لا تدخل آليًا. أسماء المنتجات القديمة المطابقة لا يعيد الاستيراد تسميتها تلقائيًا إلى الصياغة الجديدة؛ يلزم فحص عرض المنيو النهائي.
4. لم تُفحص قاعدة الإنتاج أو استُخدمت للمطابقة؛ هذه الأرقام **صالحة للقطة العامة المحددة فقط**. موافقة مستقلة ونسخة احتياطية والتحقق من الهدف الفعلي لازمة قبل أي انتقال للإنتاج.
